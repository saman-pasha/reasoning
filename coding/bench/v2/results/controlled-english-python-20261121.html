Controlled English effect on Python codegen

Does the requirement, said again in controlled English after the requirement itself, make Python's first program right more often? One hard task, mvccs_acid (a multi-version B-tree with transactions and snapshot isolation), written by claude-sonnet-5-5 at effort low. Sixty trials an arm, the two arms shuffled together in one run.

120 cells, 186 generator calls, 849 900 tokens and 35 min of cell time: $4.69 at list prices.

The answer

It did not repeat.

The same test, asked again in a run of its own with a new seed (controlled-gzip-python-20261121), found 34/60 against 30/60, p = 0.29. Read the result below as one run's.

Yes. The controlled restatement makes the first program right more often: 37/60 against 25/60, p = 0.022.

The test was written down and committed before the first cell ran: first-attempt passes, Fisher's exact test, one-sided, significant at p < 0.05. The result passes it. (Two-sided, p = 0.044.)

It also costs less.

With more first programs right, the arm made 84 calls against 102 (−18 %) and spent 9 % fewer tokens and 20 % less time, though the note adds 2 590 characters to every call. These figures are described, not tested.

It works through one word the requirement does not name.

Python's first programs fail almost only at the error case, which expects the word error. The note says "causes an error" in two sentences of its own, and 39 of its 60 first programs print the word, against 27 of 60 with the requirement alone.

It is no general aid.

The same note makes guided cocolog's first program right far less often (2/20 against 15/20), through its sentences on input. In C and in cocolog without its guide it changes nothing.

The test, chosen before the run

The earlier run of these two arms, reason-python-20261121, gave 12/20 against 7/20 (two-sided p = 0.21). The gap was large, but twenty trials an arm cannot tell a gap of five cells from chance, and that arm was the best of five notes. So this run asked the one question again, with three times the trials and a new seed. Its README, committed in cbb2150 before any cell ran, says:

  • Hypothesis: the controlled note makes the first program right more often than the requirement alone.
  • Measure: first-attempt passes: the first program passes the eight repair cases and the two held-out cases.
  • Test: Fisher's exact test, one-sided (controlled greater), significant if p < 0.05.
  • Everything else (the final pass, calls, tokens, the error case) is described and not tested.

Why it works here

As in every Python run before it, the first programs fail almost only at the error case. That case sends commands to a transaction that has not begun, then a second begin, and expects error five times. The requirement says "error if T is not active" and never what an error prints.

Limits

  • One task, one model, one language. The effect goes through one word that the cases expect and the requirement does not name. A requirement that names its outputs would likely not show it; that is not tested.
  • The same note harms guided cocolog (2/20 against 15/20, and 0/10 against 6/10 in the ablation), through its four sentences on input.
  • The restatement was written by hand, by the assistant that ran the benchmark, from the requirement alone. Its cost is not counted, and another writer would make another text.
  • One cell met the safety classifier. Both repair calls of one plain cell were refused (reasoning_extraction). Its first program had failed already, so the test does not change. It is that arm's one final failure.
  • The note sits in the user prompt, not in the system prompt as the coding endpoint puts its notes.
  • The model takes no temperature, and the same prompt passes at different rates in different runs, so only arms of one run are compared.
