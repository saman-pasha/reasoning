## What the comparison says

- **Python is the only language that passes every cell on the first
  attempt.** All nine cells pass at attempt 1. Its per-cell prompt is
  279-392 tokens.
- **C's six passes are first-attempt passes; its three failures are all
  `lcs` held-out.** The generated program is a correct DP over
  `scanf("%100s")`; the greedy-killer held-out case (`aggtab`,
  `gxtxayb`) passes, and the empty second line (`abc`, then an empty
  line) makes `scanf` return no second string, so the program exits
  without printing. The three trials return the same program (trial 3
  differs from trial 1 by one blank line) with the same token counts
  (92 prompt and 235 completion each). This is the held-out case the
  task was built around, not a harness fault.
- **SWI's three `lcs` cells fail every repair case for one reason: the
  program prints the answer and then a second `0`.** `lcs([], _, 0)` and
  `lcs(_, [], 0)` are both choice points, so `main` prints one line per
  solution; the exact policy refuses the extra line. The retry prompt
  repeats each time and the model returns the same defect. `stable_sort`
  and `calculator` pass 5/6 at attempt 1 and 6/6 final.
- **cocolog's low pass@1 is not one failure.** `stable_sort` repairs
  every cell (2, 2 and 3 attempts; final 3/3). `lcs` passes 2/3; its one
  held-out failure is a wrong recurrence (it returns 2 for
  `aggtab`/`gxtxayb`). `calculator` never gets valid code: the generated
  program writes the character code for `(` as `0'(` and the cocolog
  reader raises `Syntax error: Operator expected`; all three attempts
  fail at that line, and the repair loop does not mend it.
- **The token difference is the guide, not the model's answers.**
  cocolog's normal generator carries about 19 000-20 000 prompt tokens
  per call (19 171 on the successful `lcs` calls; about 60 000 for a
  three-attempt cell). C, Python and SWI prompts are 92-392 tokens.
  cocolog spends 95.5 % of the run's tokens and finishes 5/9.
- **Python's wall time is startup, not thinking.** Each Python cell pays
  about 3 s per case for the pyenv `python3` shim (six cases per verify),
  so it is the slowest language despite being the cheapest after C in
  tokens. SWI is fastest.

## Confounds, as stated before the run

- Each language uses its **normal generator**, not one common prompt. C
  uses `codegen_c`, Python `codegen_python`, cocolog `codegen_cocolog`,
  and SWI a short direct prompt. The comparison measures language plus
  guide. A different cocolog or SWI prompt is a different experiment.
- Non-C languages get a **10 s case timeout**; C keeps its 3 s. The
  allowance is for interpreter startup, not a policy change for C.
- Three trials per cell and one model: the table is a pilot, and a
  per-language interval over three tasks would be too wide to be an
  estimate.
- Held-out cases are run only after the repair cases pass. A held-out
  failure is final and is not described to the model.

## Repair diagnostics after this run

The run above was taken with diagnostics that gave only
`file:line:column` for a load error, and nothing for a cocolog entry goal
that failed silently. Two harness fixes are in `langs.pl`
(`reasoning 1.8.21`):

- a load error now includes the offending source line and a caret under
  the column, unless the compiler already quotes the line (GCC and
  Python do);
- a cocolog run that exits nonzero with empty stderr is rerun once under
  `--trace`, and the first case's diagnostic gets the tracer's last
  failing chain, one line per depth.

A rerun of `calculator/cocolog` trial 1 with the source-line fix
(61 390 tokens) mended the `0')'` syntax error on attempt 2: the model
could finally see the line. The failure then moved to a silent goal
failure, which is what the tracer covers. A second rerun with both fixes
(62 892 tokens) began with a different, arithmetic error, so the tracer
did not fire; its backtrace names the failing goal `'1'>='0'` and the
caller chain, and attempts 2 and 3 repeat the same text. A fourth manual
attempt (21 528 tokens) repeats it too: the model keeps treating
one-character atoms as numbers (`C >= '0'`, `D is C - '0'`). That is the
model's cocolog arithmetic, not a blind loop; the diagnostic names the
goal exactly. The silent-failure tracer is pinned by the test
(`main :- fail.`), not by this cell. The 36-cell table above remains the
record of the run before these diagnostics; the diagnostics changed no
guide or model prompt. The cocolog guide paragraph below is a separate,
stated change.

## cocolog guide paragraph after this run

The cocolog child appends one benchmark paragraph to the language's
normal guide (`reasoning 1.8.22`):

```text
A character is not a number. atom_chars/2 gives one-character atoms; to
compare or subtract one, take its code with char_code/2, or keep the
character codes that read_line_to_codes/2 returns. Write a character code
as 0' and the character itself: 0'( is the code of (, 0') of ), 0'0 of 0.
The token ends at the character; never add a quote after it. 0'0 is the
number 48; '0' is an atom and not a number.

A parser over codes works on non-empty list patterns: [C|Cs] binds C, and
only then compare it (C =:= 0'+). A spaces predicate has three clauses:
skip the whitespace with a cut; skip_spaces([], []). for the end; and
skip_spaces(List, List) :- List = [_|_]. for a non-space code, so a
non-space is returned unchanged (never skip_spaces(Rest, Rest)., which
also matches an unbound list). A parenthesized atom binds C and its tail
Cs, compares the open with C =:= 0'(, recurses on the tail Cs (not on the
list that still begins with the open paren, or the parser loops), and
after the inner expression and the spaces compares the close with
C2 =:= 0'), as two separate comparisons. The digit collector ends with
parse_digits(Rest, [], Rest). and no Rest = [] guard: the remaining codes
may be a non-empty suffix. number_codes/2 takes the list of digit codes
and gives the number; it has no third argument, so collect the digit
codes and the remaining codes yourself. library(stream) already defines
digits/3, and a digits/3 of your own is ignored: name the collector
parse_digits/3.
```

It is a cocolog-only deviation from "language plus its normal guide";
the 36-cell table above predates it. The paragraph was built from the
published cell's errors, each step checked by a paid rerun:

- The `char_code/2` line and the `0'` token rule stopped the
  one-character-atom arithmetic; the model still wrote `0')'` until the
  rule was stated positively and the wrong forms were removed.
- `number_codes/2`, the three-clause spaces predicate, the recursion on
  the parenthesis's tail and the digit base without `Rest = []` removed
  the unknown procedure, the instantiation error and the timeout.
- `library(stream)` defines `digits/3`, and a user's `digits/3` is
  silently ignored. This was the last blocker: the model's collector
  was never called. With the rename to `parse_digits/3` the cell passed
  at attempt 1.

With the final paragraph, `calculator/cocolog` over the benchmark's
three trials: **2/3 pass@1, 3/3 final, 1.33 attempts, 82 423 tokens,
25.8 s** (the published run was 0/3, 0/3, 186 407 tokens). Two trials
passed on attempt 1, one on attempt 2. JSONL:
`cocolog-guide-20261117.jsonl` (taken from commit `91dcb4d` with the
guide uncommitted; committed with `reasoning 1.8.22`).

A one-trial check of all three cocolog tasks with an earlier version of
the paragraph (before the last two parser rules) read `stable_sort` to a
final pass in 2 attempts and `calculator` to a final pass in 3, and left
`lcs` with a repaired program that fails its held-out case: it returns 1
for `aggtab`/`gxtxayb` (the correct length is 4), a wrong LCS recurrence
the guide does not address. The final paragraph was not rerun on `lcs`
or `stable_sort`.

The guide was built over nine paid checks on the failing cell; they cost
754 684 tokens in all, including the final three-trial run of 82 423. No
other language's prompt changed.

`fail_generator` because the parent passed the child its arguments in a
different order than the child read them (0 tokens, 33.8 s). The child

`--diag`), and the test pins their order independence. A one-cell Python
`lcs` smoke run then passed at attempt 1 (473 tokens, 22.0 s), and the
grid above is the record.
