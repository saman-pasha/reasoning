The model-written controlled note in Python codegen

Since reasoning 1.18.0 the coding endpoint writes its controlled English note itself: a model says the requirement again, and the grammar keeps each sentence it reads. Three earlier runs measured a note written by hand. Does the note the endpoint writes, with no hand-written text, have the same effect?

120 cells, 232 calls, 1 218 359 tokens, 46 min of cell time, $6.35. The note itself: 3 calls, 12 624 tokens, $0.05.

The answer

No. It made the first program right less often: 7/60 with the note, against 18/60 without it.

The test written before the run asked whether the note helps: one-sided p = 0.997, not supported. The other direction was not tested before the run; two-sided p = 0.023, described.

The loss is at the error case.

With the note, 7 first programs of 60 contain the word error at all, against 27 of 60 without it. Every program that failed the error case printed nothing there.

It costs more.

21 % more calls and 48 % more tokens than the requirement alone.

"Print error": first programs that contain the text error. The error case expects the word error five times, a word the requirement never names (it says "error if T is not active"). The 14 programs that did not compile had an unterminated string (8), or ≥ and → in the code (3 each).

What the two notes say about output

The model's note says which commands print and what, and of an error only "causes an error":

Every r_command that names an inactive_transaction causes an error.
Every p_command that names an empty_view prints nothing.
Multiversion_Tree does not print a prompt.
Multiversion_Tree does not print a debug_output.

The hand-written note also says "causes an error" and has the same two last lines, and it also has Every command prints an answer. The model's note does not have that sentence, and the requirement does not say it in those words: b, i and d print nothing when they succeed. That is the plainest difference at the error case, but no run took the sentence out or put it in. It is a reading of the counts, not a tested cause.

What this means for the endpoint

Since reasoning 1.18.0 the coding endpoint sends this kind of note for C and Python by default (CODING_ENDPOINT_CONTROLLED_LANGS, c,python). The gain measured before was the hand-written note's. On this task the note the endpoint writes harms Python's first program. CODING_ENDPOINT_CONTROLLED_LANGS=none sends no note.

Limits

  • One task, one model, one language, one note. Another note the model wrote could read differently, and no second note was made to choose from.
  • The cause is read from the counts; no arm took a sentence out or put one in.
  • One refused cell counts as it came.
